本轮按整体建设安排，三路子 Agent 分工开发，主 Agent 合并、补充证据预算策略与读取优化。该报告区分已完成开发、验证结论和剩余工作；不是长期记忆内容的质量确认。

## 验证与性能

本地集成检查：339 项 Python 测试、11 项 Node 测试通过。合成评测使用临时 SQLite，完全不包含私人对话或生产原文。

10 万记录合成集：可信上下文读取中位耗时约 1.91 秒降至 0.079 秒，分配峰值约 225 MB 降至 4 MB；证据包约 15.51 秒降至 2.70 秒。候选读取峰值仍约 217 MB，属于下一轮必须继续处理的问题。这不是生产负载或真实 p95，也不代表召回质量提升。详见 [比较报告](READ-COST-OPTIMIZATION-COMPARISON-2026-10-03.md)。

开发不调用 LLM；未恢复全量提炼、放开预算、修改私人记忆或将候选升格。上次用量回执累计约 2,287,578 / 3,000,000 tokens，仍需以后台当前回执为准。

## 接下来的顺序

1. **P0：实际质量闭环。** 对条件作用域、本人明确决定、第三方发言及后续更正建立固定测试集；旧失败用例保持失败，独立复核后才允许扩大提炼。
2. **P1：候选内部有界读取。** 保持准确总数、权限与上下文版本语义，优化候选查找和原文索引；补测有原文的证据包及真实 PostgreSQL 成本。
3. **P1：真正可用的 personal。** 从高价值候选提出少量带出处的个人背景，由本人确认确切陈述后纳入；不能把原子库的 159 条判断直接搬成已确认事实。
4. **P1：上游一致性。** 用真实文档或会议验证 LocalVault 导入、幂等、角色归属、纠正和重新提炼；原件保留，处理规则带版本。
5. **P2：多 Agent 接入。** ArkClaw 先使用 personal 只读；以后写入独立 inbox，只形成候选。上游写入 Skill 和下游渐进式加载 Skill 配合 MCP；不自动加载整个记忆库。
6. **P2：工作台易用性。** 明确候选/可信/历史的状态，展示来源、有效时间和审核动作，让人工补充、修订和重提炼结果可追溯。

部署回执另记，发布前通过恢复数据库验证与 GitHub CI；代码发布不包含新生产迁移、模型执行或数据升格。
