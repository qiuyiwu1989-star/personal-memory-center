# 第三轮：长来源离线分段规划

新增 `pipeline.memory_center.long_source_plan` 和 `scripts/plan_long_source.py`。本轮只做离线规划与独立收据检查，未接生产 worker、未提炼、未调用模型、未读取预留评测正文。

`plan_long_source` 复用现有 `prepare_imports` 校验与 archive 载荷生成，但在规划前确保每段正文不超过 20,000 Unicode 字符。这是适配 scope_review/UI 的保守边界；Store 的载荷硬限是 `encoded(messages)` 不超过 24,000 字符，并非单条正文 20,000 字符硬限。也不把字符限制说成 token 或字节限制。既有 import_adapter v1 及 part keys 没有修改。

每段保留原始消息序号、ID、角色、局部偏移、全局偏移、文本 SHA、整份消息规范 JSON SHA 和稳定 segment ID。全局偏移定义为各消息正文依次拼接，不插入分隔符；跨消息作者、时间、标题仍各自保存，不合并或猜测人物。内容变化产生新 ID；同源重试保持 ID 与载荷稳定。归档载荷保留已有来源元信息，定位器仍受现有 1,000 字符限制。

`verify_long_source_plan(plan, original_messages)` 独立遍历原文，检查每段 SHA、ID、内容、角色、归档载荷、导航、顺序、连续覆盖及账本。缺段、重叠、修改内容、改成已批准状态均拒绝。检查需要完整原始消息；SHA 是绑定工具，不是来源真实性证明。纯空白消息或不能满足限制的超长空白区间会整体拒绝，不静默丢弃。

完整前后文通过消息 SHA、原始 ID 和相邻消息索引导航回原件，明确标为 `navigation_only_not_evidence`。只要原消息含条件标记，各段都要求条件语义复核；这只是保守提示，不判定条件真实范围。分段未释放条件、未确认身份、未把导航文本算成引用证据，也不改 v17/v21 evidence 路由。原件必须继续独立归档。

CLI 输入是私有 JSON：`source_key`、`scope`、`source_type`、`source_metadata`、`messages`；输出含正文，必须在公开仓库外。输出用 0600 权限排他创建，禁止覆盖，错误只打印通用信息。路径守卫只保护当前公开仓库，调用者仍须选择真正的私有目录。输入上限 5 MB、1,000 条消息；不是无限文件批处理工具。

9 项合成测试覆盖长会议无损复原、显式角色、Unicode/emoji/转义载荷、21,000 ASCII 字符保守拆分、同源重试、内容变化、跨边界条件、损坏收据拒绝、空白异常与未知角色拒绝、真实本地 Store archive 重试与全局定位、CLI 私有输出与排他创建。字面覆盖成功不等于模型证据覆盖，更不等于质量通过。

后续需要：接入已授权开发组完整来源，保存私有分段收据；建立原件导航加载器；逐段跑输入覆盖检查；按原文全局位置汇总缺口；独立评分归属、时间、条件和关键遗漏。预留组仍须隔离，不能将它用于分段调参。上述线路完成之前不恢复全量自动提炼。
