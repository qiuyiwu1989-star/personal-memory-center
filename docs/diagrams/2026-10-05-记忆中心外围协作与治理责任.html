记忆中心如何与外围协作，并向你交代

外围提供可追溯的资料与变化事件；记忆中心提供可纠正、仍然有效的上下文。你通过工作台掌握来源、治理结果、权限和费用。

“已经上传”只说明资料收到；“已经提炼”只说明候选产生；只有通过归属、证据、时间与治理检查的内容，才进入当前可用记忆。原子库可以提供知识素材，不自动成为你的观点。

协作全景：三种角色，两个回路

外围交什么，中心怎么处理

外围交付“证据包”

  • 稳定的来源键、版本和分段关系。
  • 实际可见正文；作者与发言角色明确，未知就标未知。
  • 已知日期、原文定位和原件引用。
  • 可见范围：完整、仅可见部分或未知。
  • 后续变化事件与可重试的提交账本。

附件、链接、隐藏内容不能因为正文提到，就声称中心已读过。第三方建议必须保留第三方归属。

中心执行统一治理

  • 校验凭据与输入，归档并给出明确回执。
  • 由中心单独授权提炼，不让外围凭据启动付费模型。
  • 候选与证据关联；检查归属、有效时间、冲突和长期价值。
  • 保留未采用的原因与历史版本。
  • 仅把符合条件的当前内容供 Agent 读取。

低风险自动化可以逐步增加，但需要政策和评测；身份、授权与重大更正不能凭模型猜测。

向你交付“治理账本”

  • 来源清单、覆盖范围与处理状态。
  • 候选、可用记忆、未采用内容及依据。
  • 谁改了什么、何时失效、由什么取代。
  • 处理费用、失败原因、重试与暂停状态。
  • 客户端权限、方法版本与回放入口。

后台应该能从一条记忆回到原文，也能从一份资料看到它贡献了哪些记忆；这两种方向都要可追查。

你自己的知识与记忆，如何交代

原子库：知识素材

文章、概念、案例和内容片段继续保留其来源。通过适配器进入来源层，或作为知识引用按需检索。

一篇文章提到的观点，不一定是你的现行判断；不能整库直接升格。

个人记忆：可用上下文

你的明确判断、决策理由、稳定偏好、人物关系与项目状态，按相同证据规则治理。历史批次与个人范围之间需要受控升格。

范围名称不等于质量等级；“历史资料”不能只改标签就成为 personal。

工作台：你的控制面

来源 → 候选 → 当前记忆 → 被哪些任务使用，形成可追溯链。列表和检索是入口，关系图用于解释来源、对象、项目和替代关系。

图上的关系也要有证据；不为视觉丰富去猜人物关系。

更正与撤回：要补齐的闭环

建议补齐

变化提交

外围提交新版本、明确更正或撤回请求，保留父来源与分段清单。

建议补齐

中心处理依赖

定位旧来源及派生候选、记忆、文档；暂停不再有有效证据的结果，保留审计。

建议补齐

向你报告结果

列出影响对象、仍有独立证据的判断、失败与待复核内容；区分撤回可检索性和物理删除。

建议联调

Agent 刷新上下文

依据版本变化重新读取。客户端必须检查版本；中心无法收回已经发出的提示词和历史回答。

现有后台的“撤回一条记忆”与“撤回整个来源及所有派生内容”不同。LocalVault 本地删除或 tombstone，也不能直接显示远端已经撤回。

成本边界：哪些步骤需要模型

规则处理 · 无 LLM

接入与控制

权限、字段、分段、去重、归档、状态查询、版本记录与预算门禁。

按需调用 · 有费用

理解与治理辅助

提炼候选、语义核查、复杂冲突分析、中文表述与主题生成。每次处理应记录方法版本和实际用量。

中心检索 · 无 LLM

渐进式读取

先少量上下文，再查相关记忆，必要时取原文；按权限和返回预算裁剪。下游模型阅读这些内容仍消耗它自己的 tokens。

这份 LocalVault 回复：要对齐的接口事实

对方报告的是需求与自身测试情况；不能代替双方真实联调。下面按现有代码核对，不声称这轮已申请或验证 LocalVault 凭据。

议题现有实现 / 边界对接安排
会话与连接MCP 配置为 stateless HTTP，不要求持有会话 ID。实际初始化与 tools/list 仍需客户端联调；不要靠文档推测连接成功。
专用收件权限新写入凭据仅限一个 agent:*‑inbox 范围；读取个人范围另行授权。范围必须已获主人授权。核实 LocalVault 范围和实际凭据，再测跨范围拒绝；本图不签发 Token。
禁止外围付费archive_only 与服务端模型权限守卫已实现，新 Agent 凭据仅归档。纠正“只有读写，无法禁止提炼”的旧判断；具体凭据仍要测拒绝 extract / reextract。
字段与幂等parent_source_key 位于 source_metadata，不是顶层；导入回执字段是 id、job_id、duplicate。相同主体、范围、来源键及规范化内容去重；同键不同内容可生成新记录，不是强制冲突。需要明确版本约定。
长度与元数据来源键最多 300 个 Python Unicode 字符；最多 100 条消息，规范化消息 JSON 最多 24,000 字符。元数据白名单见下方。客户端不能使用 UTF‑16 长度或整个请求体长度替代该判定；留出余量并先用合成输入对齐。
源级撤回现有 MCP 未提供完整的来源撤回工具。父来源字段不自动形成批量撤回机制。先设计影响回执和可重试契约，再开发并验证派生结果失效。
空结果与错误工具错误可能通过 HTTP 200 返回 isError:true；上下文同时含 total、truncated 与版本。不能只看 HTTP 状态；空结果不证明全局没有记忆。稳定错误码、可重试性与分层错误还需完善。
现有元数据字段与实现依据

original_ref / original_date / author / locator / parser_version / parent_source_key / visibility：仅这些键，各值为字符串，最多 1,000 字符；visibility 为 unknown、visible_only 或 complete_visible。未知键拒绝；外围的完整路径、修改时间和同步内部信息优先留在自己的账本。

定位符目前是受长度限制的字符串，不表示服务端理解或验证每种定位语法。source_title 与 created_at 为可选消息字段，当前不应把日期长度校验当作日期真实性验证。

实现依据：pipeline/memory_center/service.py、core.py、source_metadata.py、agent_credentials.py、governance.py。已核对当前代码与此前冻结的线上版本来源；本轮未进行 LocalVault 的实网验收。

建议实施顺序

  1. 先冻结最小对接契约：权限、实际 schema、长度单位、版本键、回执和错误分类。
  2. 小批量归档联调：重复提交、第三方发言、未知日期、部分可见与跨范围拒绝，先不触发付费提炼。
  3. 补齐向主人交代的双向账本：每份来源贡献了什么，每条记忆由什么支持，处理费用和排除理由可见。
  4. 完成更正与源级撤回：验证派生记忆、文档及客户端缓存的变化，而非只改本地上传状态。
  5. 再扩大自动处理：依据质量评测逐步开放中心治理策略，并引入会议、文档和更多 Agent，复用同一证据规则。

讨论结论：中心对“什么可用、为什么可用、如何纠正”负责；外围对“资料来源与实际覆盖范围”负责；主人掌握治理政策和授权。计划项不等于已经上线。
