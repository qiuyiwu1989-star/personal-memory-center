# 真实来源输入覆盖检查 · 2026-10-04

新增 `pipeline.memory_center.input_coverage.audit_input_coverage`，不调用模型、数据库或网络，也不修改提炼路由。它核对每个 evidence 的原文偏移及非重叠性，分别报告完整来源字符、进入 evidence 的字符、被路由或跳过的字符、消息上限和方法版本。结果不携带正文，完整覆盖也不等于语义质量通过。

为什么需要这层：一份长文档可能完整归档，却没有完整进入模型可引用的片段。此时模型没有抽出记忆不能证明原文没有长期价值，更不能拿空结果通过质量评价。

本次只检查已冻结的 **开发组**：8 个完整来源单元，75,101 Unicode 字符，其中一个提取文档 74,214 字符，超过当前 scope_review 的单消息 20,000 字符限制，同时超过 Store 的整批 JSON 24,000 字符限制。直接输入当前 v21 的离线路由只产生 2,742 evidence 字符。这个数字是输入可行性诊断，不是实际模型测试或召回率，长文档尚未按接入与复核预算分段。预留组正文没有用于此轮诊断或调参。

处理建议：保留完整原件和全局偏移；长文档分段时保留作者、说话人、条件前后文及稳定分段收据；把参考文档可挖掘内容与对 Agent 的运行指令分开。重新治理前报告每段实际覆盖和未处理部分，不能静默截断。当前模块只核算，不执行这项分段改造，不自动释放条件或确认个人记忆。

输入预检查中的 `input_ready_without_segmentation` 仅表示消息数量不超过 100 及规范化整批 JSON 不超过 24,000 字符；`review_ready_without_segmentation` 另行检查单条 20,000 字符复核上限，不代表模型请求适配 token 上限；`full_evidence_coverage` 仅表示字面覆盖。独立语义评分仍需检查归属、条件、时间、关键遗漏和出处。

私有诊断 v2 更正了初步诊断的来源映射：`human_message → conversation`，`export_account_user → user`，未知文档作者保留 `external`。旧收据留存，v2 显式 supersedes，未覆盖历史。来源账号角色不证明身份或当前观点。

八项合成测试覆盖：长文档无法直接 ingest、参考文档排除、助手发言不作个人证据、错误定位拒绝、角色与重复 ID 校验、Unicode 字符与字节/token 区分。模块未接入生产 worker，未调用提炼模型，未批准质量或恢复历史队列。

更正记录：第三轮直接核对 `Store.ingest` 后，确认不存在单消息 20,000 字符接口硬限；那是 scope_review 的限制。预检 v2 分开报告整批 JSON 接口尺寸与复核尺寸，新增 21,000 ASCII 正例证明可入库但需分段复核。先前开发材料覆盖数不受此字段更正影响；旧私有诊断收据保留并由新收据显式说明，不覆盖历史。
